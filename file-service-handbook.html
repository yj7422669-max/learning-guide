파일 하나가
팀 서버에 도착하기까지

버튼 하나를 만든 것에서 시작해 로그인·조직 권한·DB·파일 저장소·자동 배포까지 연결한 기록입니다. “무엇을 입력했는가”와 “왜 그렇게 했는가”를 함께 읽습니다.

대상: 처음 서비스를 만들어 본 비전공자 · 환경: WSL Ubuntu / 팀 dev · 작성 기준: 2026년 11월 18일

이 교본은 새 설치를 지시하는 문서가 아니라, 실제로 한 일을 이해하고 다시 찾는 안내서예요. 연후님이 화면을 확인한 결과, 저장소 코드에서 확인한 사실, 팀원이 공유한 결과를 구분했습니다. 현재 파일 기능은 dev에서 검증했고, prod 배포는 별도 작업입니다.

CHAPTER 01내가 만든 것은 무엇이었나

“같은 조직의 사람들이 파일을 올리고, 보고, 내려받고, 허용된 사람만 지울 수 있는 화면”을 만들었어요.

연후님이 맡은 부분

파일 관리 화면, 파일 선택과 이름 표시, 업로드 전 검사, 실제 API 연결, 목록·미리보기·다운로드·삭제, 사용자별 삭제 버튼, 실패 안내와 목록 갱신을 준비했어요. AI가 구현을 도왔고, 연후님은 명령 실행·PR 처리·실제 브라우저 검증을 따라갔어요.

건률님이 맡은 부분

파일 API를 처리하는 서버, 파일 정보 DB 연동, SeaweedFS 파일 저장소, 조직 소속 확인 연결, 배포·경로 설정을 준비했어요. 실제 MySQL·SeaweedFS 통합 검증은 #119에 기록했어요.

CHAPTER 02MSA에서 파일 서비스가 하는 일

MSA는 큰 프로그램의 일을 여러 서비스로 나눠 연결하는 방식이에요. 우리 팀에서는 로그인, 조직·멤버, 파일, 채팅이 각각 다른 일을 맡아요. 이름만 나눴다고 MSA가 되는 것이 아니라, 서비스 사이의 요청과 권한도 맞아야 해요.

웹 화면사용자의 버튼·파일 선택연후님 파일 프론트엔드
→
Gateway주소에 따라 목적지 결정공통 입구·교통정리
→
파일 서비스권한·파일 상태·URL 발급파일 관련 처리 담당
이름쉬운 역할파일 기능과의 관계
웹 / React사람에게 보이는 화면목록·버튼·선택 파일·오류를 보여주고 API를 요청해요.
Keycloak로그인 담당로그인 후 토큰을 발급해요. “누구인가”를 증명하지만, 모든 조직의 파일에 접근을 허용하는 것은 아니에요.
user-service조직·멤버 담당파일 서비스가 “이 사람이 이 조직 멤버인가, OWNER인가”를 확인할 때 연결해요.
file-service파일 업무 규칙 담당업로드 시작·완료, 목록, 임시 URL 발급, 삭제·권한 판단을 처리해요.
MySQL구조화된 정보 보관파일명·조직 번호·올린 사람·크기·저장 키·상태 등 메타데이터를 저장해요. 파일 서비스 전용 DB·계정을 사용해요.
SeaweedFS실제 파일 내용 보관이미지·PDF·TXT의 실제 바이트를 보관해요. MySQL의 파일 정보와 구분해야 해요.
Envoy Gateway접속을 서비스별로 안내/api/files는 파일 서비스로, /chat-attachments는 저장소로 보내요.
명단과 물건을 나눠 보관한다고 생각해요.
MySQL에는 “파일 이름·주인·보관 위치”가 있고, SeaweedFS에는 “실제 파일”이 있어요. 목록이 보인다고 실제 파일을 내려받을 길까지 정상이라는 뜻은 아니에요.

코드에 나오는 S3: 이번 저장소는 SeaweedFS이며, S3 호환 API로 파일을 주고받아요. 그래서 설정 이름에 S3_ENDPOINT 등이 사용됩니다.

CHAPTER 03실제 작업을 순서대로 되짚기

기존 화면에서 연결 지점을 찾았어요

App.jsx의 조직 선택 함수가 선택한 조직을 기억하고 대시보드로 바꿨어요. Dashboard.jsx의 activeMenu가 본문에 무엇을 보여줄지 결정했어요.

왜? 파일 화면을 새 앱으로 따로 만드는 대신 기존 로그인·조직 선택·메뉴 구조에 붙이기 위해서예요.

빈 파일 화면과 파일 선택부터 만들었어요

파일 메뉴를 눌렀을 때 제목과 빈 상태를 표시했어요. selectedFile로 선택한 파일을 기억하고 이름을 보여줬어요. 처음에는 파일 선택 입력칸을 중복으로 넣어 버튼이 두 개 보였고, 하나만 남겼어요.

이때의 성공: 파일을 바꾸면 이름이 바뀜. 아직 안 된 것: 서버로 파일 전송.

로컬 웹을 켜기 위해 주변 프로그램을 준비했어요

npm ci로 웹 의존성을 설치했고 Vite를 켰어요. 로그인용 Keycloak, 조직 목록용 MySQL과 user-service도 필요했어요. Java 17을 설치해 user-service를 실행한 뒤 조직을 만들고 파일 메뉴로 들어갔어요.

업로드 전에 혼자 할 수 있는 화면 작업을 했어요

100MB 제한·선택 취소·업로드 버튼·로딩·빈 목록·실패 안내·페이지 이동을 만들었어요. 당시 파일 API가 없어서 No static resource api/files가 나왔고, 실패 안내 중에도 파일 선택이 되는지 확인했어요.

왜? API를 기다리는 동안 입력·상태·실패 대응을 먼저 준비하면 실제 연결할 때 확인 범위가 줄어들어요.

팀원의 최신 화면 변경을 합쳤어요

main에 로그아웃·멤버·초대 기능 등이 추가되며 Dashboard.jsx에서 충돌이 났어요. 최신 기능과 파일 화면을 함께 남겨 해결했고, 파일 선택·로그아웃 버튼·멤버 메뉴가 보이는지 확인했어요.

충돌은 무엇? 같은 부분의 두 수정 중 어떻게 합칠지 Git이 자동으로 결정하지 못하는 상황이에요.

#119의 실제 파일 API와 연결했어요

건률님이 목록·업로드·URL 발급·삭제 API와 프론트 요청 모듈을 준비했어요. 응답의 items, total, id, name을 맞추고, 로그인 토큰을 자동 첨부하는 기존 요청 함수를 사용했어요.

#119 파일 백엔드#102 목록·업로드·다운로드 연결

머지 후에도 이전 화면이 보이는 이유를 찾았어요

새 이미지가 만들어져 main의 태그는 바뀌었지만 dev는 이전 이미지를 실행 중이었어요. Argo CD에 Git 새로고침을 요청한 뒤 실제 이미지가 바뀌고 파드가 준비됐는지 확인했어요. 브라우저에서는 Ctrl + Shift + R로 새로고침했어요.

목록은 성공했는데 업로드가 실패했어요

팀 dev에서 목록은 나왔지만 업로드는 Failed to fetch였어요. 조회 결과 저장소 경로의 ResolvedRefs=False / RefNotPermitted, ReferenceGrant 없음, 저장소 경로 HTTP 500이 확인됐어요.

허용 설정은 Git에 있었지만 아직 실제 적용 전이었어요. 기선님도 같은 원인을 확인했고, 건률님이 설정 반영 후 재확인을 요청했어요. 이후 연후님이 업로드·목록·다운로드 원본 일치를 확인했어요.

미리보기·화면 디자인을 정리했어요

이미지·PDF 미리보기 API를 연결하고, TXT 등은 다운로드 안내를 표시했어요. 미리보기는 테두리 버튼, 다운로드는 연한 파란색으로 바꾸고 업로드 영역·파일 목록을 정돈했어요. 개인 예시 페이지는 로컬에만 남기고 Git 공유 대상에서 제외했어요.

#125 미리보기·디자인

삭제·권한·실패 대응을 묶어 마무리했어요

업로더와 OWNER에게만 삭제 버튼을 보이고 확인창을 거치게 했어요. 취소·실패·중복 클릭·마지막 페이지 복귀·목록 재시도·빈 파일 검사를 보완했어요. 자동 테스트 17개, lint, build를 통과했고 한 PR에 모았어요.

#126 삭제·권한·최종 검증 기록

버튼을 건너뛰어도 서버가 막는지 확인했어요

testuser2로 testuser의 시험 파일 삭제 API를 직접 요청했어요. 처음 401은 인증 문제여서 성공으로 세지 않았고, 인증된 새 요청으로 다시 실행해 403 “파일을 처리할 권한이 없습니다.”를 확인했어요.

무엇을 배웠나? “버튼을 숨겼다”와 “서버가 금지했다”는 서로 다른 검증이에요.

CHAPTER 04처음 로컬 웹을 어떻게 열었나

VS Code는 코드 편집기이고, 터미널은 프로그램 실행 명령을 입력하는 곳이에요. 웹 화면이 열리려면 실제 웹 프로그램을 실행해 둬야 해요. Vite는 수정한 웹 화면을 내 PC에서 열어 주는 개발용 서버예요.

환경 / 주소당시 사용 목적구분하는 방법
로컬 WSL코드·npm·Java·Docker 실행터미널 앞에 yeonhoo@DESKTOP…
localhost:5173내 PC의 개발용 웹 화면Vite 실행 중이어야 열림
localhost:8180내 PC의 Keycloak포트가 관리자/사용자를 나누는 게 아님. master와 hellocloud 영역이 다름
localhost:8081내 PC의 user-service조직·멤버 API 처리
localhost:3306내 PC MySQLDB 프로그램의 접속 포트
10.10.24.101팀 dev 웹팀 서버·팀 계정·팀 DB 사용
localhost:8091별도 작업에서 연 prod Argo CD 관리 화면파일 앱이 아님. 배포 관리 화면
localhost는 “지금 그 프로그램이 바라보는 자기 컴퓨터”예요. 내 PC의 localhost와 서버 안의 localhost는 달라요. 로컬에서 만든 계정도 dev의 계정으로 자동 복사되지 않아요.

1. 웹 실행에 필요한 파일 설치

내 PC · VS Code WSL

위 메뉴 Terminal → New Terminal. 아래 명령은 한 줄씩 입력해요.

처음 한 번 또는 의존성이 바뀐 경우
cd ~/team03-HelloCloud/services/web
npm ci
왜?npm은 JavaScript 프로젝트의 패키지 관리 도구예요. npm ci는 package-lock.json에 정해진 의존성 버전대로 설치해요.정상설치 완료 뒤 명령 입력 줄이 다시 나와요. 의존성 취약점 안내와 서버 실행 실패는 구분해요. npm audit fix를 무작정 실행해 팀 버전을 바꾸지 않았어요.
웹 서버 실행
npm run dev

당시 VITE … ready, Local: http://localhost:5173/가 나왔어요. 브라우저에서 그 주소를 열었어요. 이 터미널을 종료하거나 Ctrl + C를 누르면 웹도 꺼져요.

2. 로그인 서버 주소 지정

내 PC · VS Code WSL / 파일 편집

웹 폴더에서 예시 설정을 로컬 설정 파일로 복사했어요. 아래 복사는 파일이 없을 때만 수행하는 Ubuntu GNU 명령이에요.

cd ~/team03-HelloCloud/services/web
cp --update=none .env.example .env.local
grep '^VITE_KEYCLOAK_URL=' .env.local

확인한 주소는 VITE_KEYCLOAK_URL=http://localhost:8180였어요. 웹 환경 설정을 바꾼 뒤에는 Vite를 멈췄다가 다시 켰어요.

왜?로컬 웹과 로그인 서버는 주소가 달라요. 로그인 요청을 엉뚱하게 웹 서버로 보내지 않도록 해요. 이 grep은 로그인 서버 주소 한 항목만 확인하며 비밀번호 파일 전체를 출력하지 않아요.

3. Keycloak과 MySQL 켜기

내 PC · 별도 WSL 터미널

프로젝트 루트의 .env가 없어서 먼저 예시에서 만들었고, KC_BOOTSTRAP_ADMIN_PASSWORD와 DB_PASSWORD를 로컬용 값으로 채웠어요. 이 값은 팀 서버 비밀번호와 별개예요. 이미 만든 .env는 덮어쓰지 않아요.

cd ~/team03-HelloCloud
cp --update=none .env.example .env
# VS Code에서 .env를 열어 필요한 로컬 값을 채운 뒤 저장
cd services
docker compose --env-file ../.env up -d keycloak mysql
docker compose --env-file ../.env ps keycloak mysql
왜?Docker Compose는 compose.yaml에 정리된 프로그램들을 실행해요. --env-file은 설정값을 읽을 파일, -d는 터미널에 붙잡아 두지 않고 뒤에서 실행한다는 뜻이에요.정상Keycloak은 Up, MySQL은 초기 준비 후 healthy. Keycloak은 127.0.0.1:8180→8080, MySQL은 127.0.0.1:3306→3306으로 연결됐어요.

MySQL 계정은 처음 비어 있는 데이터 볼륨을 초기화할 때 만들어져요. 나중에 .env의 비밀번호만 바꾼다고 기존 DB 계정 비밀번호가 자동 변경되지는 않아요. 접속 실패를 해결하려고 데이터 볼륨을 지우지 않습니다.

4. 조직 API를 제공하는 user-service 켜기

내 PC · 별도 WSL 터미널

처음에는 java: not found였고 Java 17 개발 도구를 설치했어요.

sudo apt update
sudo apt install openjdk-17-jdk-headless
java -version

sudo가 물어보는 것은 WSL의 yeonhoo 계정 비밀번호예요. Keycloak·DB 비밀번호와 달라요. 설치 중 Do you want to continue? [Y/n]은 설치 진행 여부 질문이었어요.

당시 user-service 실행 명령 · 로컬 DB 값 사용
cd ~/team03-HelloCloud/services
read -rsp "로컬 DB 비밀번호: " DB_PASSWORD; echo
DB_PASSWORD="$DB_PASSWORD" \
DB_URL='jdbc:mysql://localhost:3306/user_service' \
DB_USERNAME=user_service \
OIDC_ISSUER_URI='http://localhost:8180/realms/hellocloud' \
./gradlew :user-service:bootRun
왜?Gradle은 Java 프로젝트의 검사·빌드·실행 도구예요. 프로젝트에 포함된 gradlew를 사용했어요. 앞의 설정은 프로그램이 사용할 DB와 로그인 서버를 지정해요.정상Tomcat started on port 8081과 Started UserServiceApplication. 아래의 88% EXECUTING은 서버가 계속 실행 중이라 남아 있던 표시였어요.

서비스를 켠 뒤 브라우저를 다시 새로고침했어요. 그 결과 조직 목록의 502가 사라지고 조직을 선택해 파일 화면에 들어갔어요.

다음 날 다시 켤 때 전부 설치하나요?

아니에요. 패키지 설치·.env 작성·계정 등록·Java 설치는 이미 했다면 반복하지 않아요. 보통은 Docker 프로그램 켜기 → user-service 실행 → Vite 실행만 해요. 파일 API까지 로컬로 실행하려면 별도 파일 DB·SeaweedFS·설정이 추가로 필요하며, 웹의 기본 프록시가 file-service(8082)로 자동 분기되는 것도 아니에요. 이번 실제 파일 API 검증은 팀 dev에서 했어요.

CHAPTER 05버튼을 누르면 파일은 어디로 가나

아래 버튼을 눌러 요청 순서를 바꿔 보세요. 목록·권한 요청과 실제 파일 전송은 다른 길이에요.

목록은 파일 정보 DB를 읽어요

  1. 화면이 선택한 조직 번호와 로그인 토큰을 보내요.
    GET /api/files?orgId=1&page=0&size=20
  2. Gateway가 /api/files를 file-service로 전달해요.
  3. 파일 서비스가 토큰을 검사하고 user-service에 조직 소속을 확인해요.
  4. MySQL에서 그 조직의 COMPLETED 파일 정보를 읽어요.
  5. 화면이 응답의 items와 total로 목록과 페이지를 표시해요.

파일 이름이 보인 것만으로 저장소의 파일 전송까지 검증된 것은 아니에요.

업로드는 “신청 → 실제 전송 → 완료 확인”이에요

  1. 화면이 빈 파일·100MB 상한·파일명을 먼저 검사해요. 최종 검사는 서버도 해요.
  2. POST /api/files에 조직·이름·형식·크기와 로그인 토큰을 보내요.
  3. 서버가 멤버 여부를 확인하고 임시 파일 정보와 5분 유효 업로드 URL을 발급해요.
  4. 브라우저가 발급된 주소로 실제 파일을 PUT해요. 이 저장소 요청에는 로그인 토큰을 붙이지 않아요.
  5. POST /api/files/{id}/complete로 완료를 요청해요.
  6. 서버가 저장된 크기를 확인해 상태를 COMPLETED로 바꿔요. 화면은 성공 안내 후 첫 페이지를 다시 불러와요.

큰 파일을 file-service 본문으로 중계하지 않고 저장소에 직접 보내는 구조예요. “파일 선택”은 이 전송의 시작 전 단계예요.

다운로드는 먼저 허가된 주소를 받아요

  1. 로그인 토큰과 함께 GET /api/files/{id}/download-url을 요청해요.
  2. 서버가 현재 조직 소속과 파일 완료 상태를 확인해요.
  3. 5분 유효한 임시 다운로드 URL을 돌려줘요.
  4. 브라우저가 그 URL로 저장소의 파일을 받아요. 저장소에는 로그인 토큰을 보내지 않아요.
  5. 받은 파일을 열어 원래 내용과 같은지 비교했어요.

임시 URL에는 접근 권한 정보가 있으므로 전체 URL도 채팅·스크린샷에 노출하지 않아요.

미리보기는 지원 형식의 파일을 새 탭에서 열어요

  1. 화면은 PNG·JPEG·GIF·WebP·AVIF·PDF에만 미리보기 버튼을 표시해요.
  2. GET /api/files/{id}/preview-url로 주소를 새로 발급받아요. 서버도 형식과 소속을 검사해요.
  3. 브라우저가 새 탭에서 그 주소를 열어요. 파일 서비스는 inline 표시용 URL을 발급해요.
  4. 주소 발급이 실패하면 빈 탭을 닫고 안내해요. 팝업이 막혔을 때도 안내해요.

TXT도 기술적으로 표시할 수 있지만 이번 팀 명세는 이미지·PDF만 지원해요. “가능한 기능”과 “이번에 하기로 한 범위”를 구분했어요.

삭제는 버튼 표시와 서버 권한을 모두 검사해요

  1. 화면은 로그인한 사람의 ID와 파일의 uploadedBy, 조직 역할을 보고 버튼을 표시해요.
  2. 파일명·복구 불가 안내가 있는 확인창을 열어요. 취소는 아무 요청도 보내지 않아요.
  3. 동의하면 토큰과 함께 DELETE /api/files/{id}를 요청해요.
  4. 서버가 조직 소속을 다시 확인하고, 올린 사람이거나 OWNER인 경우만 허용해요.
  5. 저장소 파일을 삭제한 뒤 파일 메타데이터를 삭제해요. 성공 응답은 본문 없는 204예요.
  6. 화면은 목록을 갱신해요. 실패하면 파일을 임의로 없애지 않고 안내해요.

저장소 삭제에 실패하면 서버는 메타데이터 삭제도 진행하지 않아요. 부분 실패와 이미 발급된 URL의 한계는 백엔드 실행 안내에 별도로 기록돼 있어요.

JWT / Bearer 토큰은 무엇?
로그인 후 받은 임시 인증 증명이라고 생각해요. API 요청의 Authorization: Bearer …에 붙여요. file-service는 이 증명이 올바른 로그인 서버에서 발급됐는지 확인하고, 조직 소속은 별도로 확인해요. 토큰 원문은 비밀번호처럼 취급해요.

CI는 어디서 보나요?

GitHub의 Actions 또는 PR의 Checks예요. 이번 npm test는 lint → API·규칙 테스트 → 웹 build 순서였어요. 삭제 PR에서는 17개 테스트가 통과했어요.

PR 단계의 release가 Skipped인 것은 정상일 수 있어요. main push 후 release가 실행되도록 팀 파이프라인이 구성돼 있어요.

이미지는 어디서 보나요?

GitHub의 Packages / GHCR에 실행용 이미지가 있어요. 웹은 idcn-web, 파일 서버는 idcn-file-service예요. 웹 화면 코드 변경은 웹 이미지를, 백엔드 변경은 파일 서버 이미지를 바꿔요.

이미지는 실제 파일 업로드 보관함이 아니에요. 프로그램 포장물이고, 사용자의 파일은 SeaweedFS에 있어요.

어느 버전이 실행되는지 어떻게 알았나

main의 deploy/values/web/values-dev.yaml에서 image.tag를 읽고, 실제 dev Deployment 이미지와 비교했어요.

# 내 PC WSL · 최신 기록만 가져오기
cd ~/team03-HelloCloud
git fetch origin
git show origin/main:deploy/values/web/values-dev.yaml
dev 서버 안 · 읽기 전용 
kubectl -n argocd get applications web-dev
kubectl -n ideaconnection-dev get deployment web -o wide
kubectl -n ideaconnection-dev get pods -l app.kubernetes.io/name=web

Synced / Healthy만 보고 끝내지 않았어요. Git이 가리킨 버전과 실행 이미지가 같은지 확인했어요. 예를 들어 #125 이후 main은 80ee004였는데 실행 이미지는 cca1e94여서 이전 화면이 보였어요.

위 태그는 당시 사례예요. 현재 버전은 달라질 수 있으므로 오늘의 값으로 고정해 외우지 않아요.

Git 새로고침은 무엇을 했나요?

Argo CD가 최신 main을 다시 읽도록 아래 요청을 보냈어요. 배포 설정 자체를 고친 것은 아니지만, 이미 활성화된 자동 동기화가 새 변경을 적용할 수 있어요. 조회 명령과는 구분하고, 담당자 간 진행을 맞춰 사용해요.

kubectl -n argocd annotate application web-dev \
  argocd.argoproj.io/refresh=normal --overwrite

새 이미지가 준비된 뒤 1/1 Running을 확인했고 브라우저에서 강력 새로고침했어요.

개선한 협업 방식
처음에는 기능마다 검토·머지를 반복했어요. 이후 관련 보완을 같은 #126 브랜치에 모아 구현·검사한 뒤 한 번에 검토를 요청했어요. 머지된 PR은 결과 댓글로 마무리하고, 검증 결과만 남기는 데 새 PR을 만들지는 않아요.

CHAPTER 07실제로 만난 오류와 해결 근거

증상만 보고 프로그램 전체가 망가졌다고 생각하지 말고, 어느 구간의 요청이 실패했는지 나눠 봐요.

① sh: 1: vite: not found

발생 위치: 내 PC 웹 폴더에서 npm run dev.

뜻: 웹 실행에 필요한 Vite 패키지가 아직 설치되지 않았어요.

처리: 같은 웹 폴더에서 npm ci → npm run dev.

해결 근거: VITE ready와 Local: localhost:5173 표시.

② HTTP 431 / ERR_HTTP_RESPONSE_CODE_FAILURE

관찰: Vite가 431을 기록했고, 로그인 경로가 웹 주소 쪽으로 잘못 이어지는 상황을 겪었어요.

뜻: 431은 요청 헤더가 너무 크다는 응답이에요. 반복 리다이렉트·쿠키 등 원인은 여러 가지라 코드만으로 하나를 단정하지 않아요.

당시 조치: 로컬 Keycloak 주소를 .env.local에서 http://localhost:8180로 맞추고 Vite를 재시작한 뒤 웹 시작 주소부터 다시 접속했어요.

구분: 잘못된 로그인 경로와 별도로 Keycloak 자체도 켜져 있어야 했어요. 주소 수정만으로 모든 의존 프로그램이 실행되는 것은 아니에요.

③ localhost:8180 연결 거부

뜻: 해당 주소에서 응답할 프로그램이 없거나 접속이 되지 않는 상태예요.

처리: Docker Compose로 Keycloak 실행 후 상태 확인.

해결 근거: Docker 상태 Up과 실제 HelloCloud 로그인 화면 표시.

④ .env 파일 없음 / 필수 비밀번호 값 없음

couldn't find env file은 지정한 파일이 없는 것이고, KC_BOOTSTRAP_ADMIN_PASSWORD·DB_PASSWORD 누락은 파일에 필요한 값이 비어 있는 것이에요.

루트 .env.example을 .env로 복사하고 로컬용 값을 직접 저장한 뒤 재실행했어요. cp -n 경고는 그 복사 옵션의 이식성 안내였고 핵심 실행 실패 원인과 구분했어요.

이것은 팀 서버 비밀번호를 바꾼 작업이 아니에요. 비밀번호 원문을 Git·채팅으로 공유하지 않았어요.

⑤ 로그인 후 조직 목록 API 502

뜻: 웹은 열렸지만 뒤의 API 서버 연결에서 문제가 났어요. “조직이 0개”와 “조회 실패”는 달라요.

당시 원인·처리: MySQL을 켜고 Java 17을 설치한 뒤 user-service를 DB·Keycloak 설정과 함께 실행했어요.

해결 근거: MySQL healthy, Started UserServiceApplication, 브라우저 새로고침 후 조직 목록 정상.

기동 직후의 health: starting은 바로 실패라고 단정하지 않고 준비 완료를 확인했어요.

⑥ Invalid username or password

화면이 master 영역이면 관리자 로그인이고, hellocloud 영역은 앱 사용자 로그인이에요. 일반 사용자는 웹 시작 주소에서 로그인해야 해요. 로컬·dev 계정 저장소도 별개예요.

8180을 관리자 전용 포트라고 이해하지 않아요. 같은 Keycloak이 주소의 realm에 따라 다른 로그인 영역을 제공해요.

⑦ No static resource api/files / api/orgs/…/invitations

뜻: 요청을 받은 프로그램에 그 경로의 API가 없다는 의미였어요.

파일 API 준비 전 로컬 웹은 모든 /api를 user-service 8081로 보냈어요. 그곳에 파일 API가 없었으니 실패 안내를 먼저 검증했어요.

초대 API도 예전 Java 프로세스가 실행 중이면 새 코드가 자동 반영되지 않아요. 실제 실행 버전·접속 목적지·프로그램 재시작 여부를 확인해야 해요.

⑧ 목록은 되는데 업로드 Failed to fetch

서로 다른 길: 목록은 파일 서버와 DB를 읽고, 실제 업로드는 저장소 주소로 가요.

당시 직접 확인한 사실: seaweedfs-s3-route는 Accepted=True지만 ResolvedRefs=False / RefNotPermitted. seaweedfs namespace에 ReferenceGrant가 없었고 저장소 경로는 HTTP 500이었어요.

왜 막혔나: Gateway 경로는 ideaconnection-dev에, 저장소 Service는 seaweedfs에 있었어요. 다른 작업 공간의 저장소를 참조해도 된다는 허용이 필요했어요.

Git과 실제 서버 차이: 허용 YAML은 #119에 있었지만, 해당 파일을 관리할 seaweedfs-dev 앱 등록·이관은 당시 진행 전이었어요. 머지된 파일이 있다고 모든 설정이 자동 적용되는 구조는 아니었어요.

처리: 기선님도 동일 상태를 공유했고 건률님이 설정을 반영했어요. 이후 브라우저 업로드·다운로드를 다시 확인했어요.

주의: Failed to fetch만으로 ReferenceGrant가 원인이라고 단정할 수는 없어요. URL·네트워크·CORS 같은 가능성 중 실제 조회에서 발견한 차단 요인이었고, 반영 후 성공으로 연결을 검증했어요. SeaweedFS 전체 이관이 완료됐는지까지 이 결과로 대신하지 않아요.

⑨ 머지했는데 이전 디자인이 보여요

머지 → 이미지 빌드·업로드 → Git 태그 갱신 → Argo CD 반영 → 새 파드 준비 → 브라우저 새로고침 순서예요. 이 중 하나가 남으면 이전 화면일 수 있어요.

당시 Actions 성공과 main 이미지 태그를 확인한 다음 실제 Deployment 태그를 비교했어요. 새 태그·1/1 Running을 확인한 뒤 Ctrl+Shift+R로 새로고침했어요.

⑩ 삭제 API 401 → 다시 실행해 403

401: 서버가 로그인을 인정하지 못했어요. 토큰 만료·인증 헤더 누락 등 여러 가능성이 있어 당시 원인을 하나로 확정하지 않았어요.

처리: testuser2의 정상 목록 요청을 기준으로 인증 정보를 유지하고 주소·method만 수정해 재요청했어요.

403: “파일을 처리할 권한이 없습니다.”가 왔어요. 이 요청에서는 인증된 다른 멤버의 삭제를 서버가 거부한 증거예요. 401을 권한 차단 성공으로 기록하지 않았어요.

⑪ git diff 화면에 갇힌 것 같아요 / UI 리뷰와 Checks가 헷갈려요

git diff가 긴 내용을 페이지로 보여주고 있다면 q로 나와요. 프로그램을 지우는 동작이 아니에요.

PR의 초록 Checks는 자동 검사 결과예요. 사람의 리뷰·팀장님의 머지 승인과 별개예요. Update branch는 최신 main을 작업 브랜치로 가져오는 기능이고, Squash and merge는 작업을 main으로 합치는 기능이에요.

CHAPTER 08삭제 버튼을 숨긴 것과 서버가 막은 것

사람자기 파일같은 조직의 다른 사람 파일
일반 MEMBER삭제 가능삭제 불가
조직 OWNER삭제 가능삭제 가능
해당 조직 멤버가 아닌 사람조직 소속 검사에서 차단해야 해요. 별도 조직 간 검증 항목이에요.

권한은 계정 이름으로 고정되지 않아요. testuser가 OWNER였기 때문에 모든 파일에 삭제 버튼이 보인 것은 정상이었어요. 같은 계정도 조직에 따라 역할이 다를 수 있어요.

화면의 검사

토큰의 사용자 ID(sub)와 파일의 uploadedBy를 비교하고 조직 역할을 봐요. 자기 파일 또는 OWNER에만 삭제 버튼을 보여요.

목적: 실수를 줄이고 사용자가 할 수 있는 행동을 보여줘요.

서버의 검사

삭제 API가 토큰·현재 조직 소속·업로더/OWNER 조건을 다시 검사해요. 화면 정보를 믿고 삭제하지 않아요.

목적: 사용자가 버튼을 건너뛰어 요청해도 실제 데이터를 보호해요.

직접 했던 검사: 시험 파일 ID 11

  1. testuser가 권한검사용.txt를 올렸어요. 이 검사는 권한 문제가 있으면 파일이 지워질 수 있으므로 버려도 되는 시험 파일만 사용했어요.
  2. 같은 조직의 일반 멤버 testuser2로 로그인했어요. 파일 목록에는 보이지만 삭제 버튼이 없었어요.
  3. Chrome F12 → Network에서 파일 목록 옆 새로고침을 눌렀어요. 도구를 연 뒤 요청해야 기록이 보여요.
  4. files?orgId=…의 Response에서 시험 파일의 실제 id=11을 찾았어요. 예시 번호와 실제 번호를 구분했어요.
  5. 정상 인증된 목록 요청을 우클릭 → Edit and resend as fetch. 하단 콘솔에 생긴 요청에서 URL과 method만 수정했어요.
요청 주소: http://10.10.24.101/api/files/11
요청 방식: DELETE
나머지 인증 헤더: testuser2의 정상 요청에서 유지

브라우저가 생성한 코드는 로그인 토큰을 포함해서 교본에 전체를 싣지 않아요. 콘솔 붙여넣기 경고를 allow pasting으로 우회하지 않았어요. Edit and resend도 콘솔에 코드를 보여주므로 내용을 확인하고 시험 대상만 요청해야 해요.

{
  "detail": "파일을 처리할 권한이 없습니다.",
  "instance": "/api/files/11",
  "status": 403
}
이 응답으로 말할 수 있는 것
“같은 조직의 다른 일반 멤버가 타인의 파일을 지우려고 직접 API를 호출해도 서버가 거부했습니다.”
이 응답 하나로 말할 수 없는 것
다른 조직의 파일 목록·다운로드가 모두 차단됐다는 뜻은 아니에요. “다른 멤버의 삭제”와 “다른 조직의 접근”은 다른 시험이에요. OWNER의 삭제 허용도 별도 확인했어요.

팀 dev용 Chrome을 열었던 방법

팀 서버의 내부 주소는 내 PC에서 바로 닿지 않을 수 있어요. SSH 연결 통로를 켜고, 그 통로를 쓰는 별도 Chrome으로 접속했어요.

① 내 PC · VS Code WSL · 실행 후 계속 켜 두기
팀 내부망 연결 통로
ssh -N -D 127.0.0.1:1080 t3-dev-cp

-N은 서버에서 별도 명령을 실행하지 않는다는 뜻, -D 1080은 내 PC에 SOCKS 프록시 통로를 연다는 뜻이에요. 아무 문구 없이 대기해도 정상일 수 있어요.

② Windows PowerShell · WSL 아님
팀 dev 전용 Chrome 실행
& "C:\Program Files\Google\Chrome\Application\chrome.exe" --proxy-server="socks5://127.0.0.1:1080" --unsafely-treat-insecure-origin-as-secure="http://10.10.24.101" --user-data-dir="$env:TEMP\chrome-t4" "http://10.10.24.101"

웹 로그인 라이브러리가 요구하는 브라우저 기능 때문에 당시 HTTP dev 주소만 안전한 주소로 취급하는 옵션을 사용했어요. 내부 개발용 임시 방법이며 운영 HTTPS 설정을 대신하지 않아요. 별도 프로필을 사용해 일반 Chrome과 구분했어요.

팀 dev 계정으로 로그인 → 조직 선택 → 파일 관리로 들어갔어요. 로컬 계정, Argo CD admin 계정을 쓰지 않았어요.

조회할 서버에 들어가기

내 PC WSL에서 입력
ssh t3-dev-cp

접속 뒤 실제 서버 이름이 lab@t4-dev-cp로 보여도, 로컬 접속 별칭이 t3-로 저장돼 있어서 그런 것이었어요. prod는 별도 별칭 t3-prod-cp예요.

서버에서 내 PC로 나오기
exit

서버에 접속하는 것과 로컬 웹을 켜는 것은 다른 작업이에요. npm run dev는 로컬 웹이 필요할 때 내 PC의 웹 폴더에서 실행해요.

오류를 공유할 때의 순서

어느 환경 / 누가 / 무엇을 / 어떤 결과 / 어디까지 확인했는지를 말하면 돼요.

예: “dev에서 일반 멤버 testuser2로 확인했습니다. 목록은 성공했지만 업로드가 실패했습니다. 저장소 경로에 RefNotPermitted가 있고, ReferenceGrant가 없습니다. 설정 반영 후 다시 확인하겠습니다.”

원인이 확실하지 않으면 “이것 때문이라고 확정” 대신 관찰한 사실과 아직 확인할 것을 구분해요. 비밀번호·JWT·서명 URL을 첨부하지 않아요.

CHAPTER 12질문을 받으면 이렇게 설명하기

“이름·조직·주인·크기 같은 정보는 파일 서비스의 MySQL에, 실제 파일 내용은 SeaweedFS에 저장됩니다. 브라우저는 파일 서버가 발급한 임시 주소로 저장소에 직접 업로드합니다.”

“로그인은 됐는데 왜 파일을 못 지워요?”

“로그인은 누구인지 확인하는 것이고, 삭제는 별도 권한입니다. 같은 조직의 일반 멤버도 다른 사람이 올린 파일은 지울 수 없습니다. 파일을 올린 사람과 조직 OWNER만 삭제할 수 있습니다.”

“삭제 버튼만 숨기면 되는 거 아니에요?”

“사용자가 요청을 직접 만들 수 있어서 서버도 검사해야 합니다. 실제로 버튼이 없는 계정으로 DELETE를 보냈고, 서버가 403을 반환하는 것까지 확인했습니다.”

“목록은 됐는데 업로드는 왜 안 됐어요?”

“목록은 파일 정보 DB를 읽는 길이고, 업로드는 실제 저장소로 가는 길이기 때문입니다. 당시에는 Gateway에서 다른 작업 공간의 저장소를 참조할 허용 설정이 없어 막혔습니다. Git에는 파일이 있었지만 실제 서버에 적용되지 않았고, 반영 후 업로드가 성공했습니다.”

“CI/CD를 했다는 증거는 어디 있어요?”

“PR Checks와 Actions에서 검사·빌드 결과, Packages에서 이미지, main의 values에서 이미지 태그를 보여드릴 수 있습니다. dev에서는 Deployment의 실제 이미지와 파드 준비 상태를 비교하고, 마지막으로 브라우저 동작을 확인했습니다.”

  2. #126: 구현 설명, 리뷰, 자동 검사와 dev 최종 검증 댓글.
